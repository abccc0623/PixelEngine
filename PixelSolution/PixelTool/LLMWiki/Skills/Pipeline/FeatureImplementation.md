# 파이프라인: 기능 구현

신규구현의 일감을 받거나 버그수정·기능변경·코드개선 요청을 직접 받을 때 읽는다. 테스트에서 실패해 돌아온 일감은 기존 일감의 ID와 기획 목표를 유지하고, 이번 구현 유형을 **버그수정**으로 다룬다. 전달된 실패 항목만 수정한다.

코드를 추가하거나 수정하는 요청일 때만 `wiki/Skills/Code/Ponytail.md`를 한 번 읽고 구현 선택에 적용한다. 같은 요청에서 다시 읽으면 내용 대신 이미 읽었다는 결과가 나온다. 설명·자료조사·일감 문서 작성만 하는 요청에는 적용하지 않는다.

1. 신규구현은 일감의 기능 내용, 주의사항, 완료 확인 항목과 선행 일감을 확인한다. 다른 유형은 요청과 현재 코드에서 완료 확인 항목을 정한다.
2. 선행 작업부터 하나씩 구현한다. `get_asset_layout`이나 파일 검색으로 확인한 실제 경로만 읽고, API 문서는 `search_wiki` 결과의 문서 ID 또는 `Doc/...`·`Lua/<모듈>.lua` 이름으로 읽는다. `.pxm`에 새 동작을 구현하거나 구조를 바꿀 때는 수정 파일을 정하기 전에 `LuaConceptGuide.md`를 읽고 관련 객체의 책임을 나눈다. Scene이 필요한 작업은 `Doc/Other/Scene.md`와 파일 생성 도구를 확인한 뒤 구현 경로를 정한다. 현재 프로젝트의 관련 파일과 엔진 API를 확인하고 요청 범위만 수정한다.
3. `patch_project_file`에서 원문 불일치나 해시 오류가 나면 해당 파일의 수정 구간을 다시 읽고 반환된 최신 해시와 정확한 원문으로 한 번 재시도한다. 실패한 추측 문구로 반복 호출하지 않는다. 구현이 막히면 확인한 장애와 중단 지점을 응답에 명시하고 미구현 일감을 완료로 표시하지 않는다. 이미 만든 일감은 보존하며 다음 요청에서 재사용한다. 도구를 실제로 호출해 연결 오류를 받은 경우에만 도구 연결 실패라고 설명한다.
4. 바뀐 파일과 구현한 결과를 완료 확인 항목에 연결한다. 구조 리팩터링을 요청받았다면 대상 객체의 책임이 실제 파일에 분리됐는지 확인하고, 일부 함수만 정리했다면 전체 리팩터링 완료로 보고하지 않는다. 구현만으로 동작을 확인했다고 기록하지 않는다.

버그수정·기능변경·코드개선은 구현에 성공한 뒤 예약한 일감에 `Editor_WorkItem_Update` MCP로 변경 유형, 실제 수정 내용과 파일을 이력으로 추가한다. `read_project_work_item`이 반환한 최신 `sha256`을 전달한다. 해시가 달라졌다면 다시 읽고 확인한 뒤 재시도한다. 구현되지 않은 내용을 이력에 쓰지 않는다.

구현한 일감을 `wiki/Skills/Pipeline/Test.md`의 테스트 단계로 넘긴다.
