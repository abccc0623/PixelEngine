# 파이프라인: 일감생성

요청 분석 결과가 **신규구현**일 때 읽는다.

요청한 완성품과 비슷하고 널리 알려진 게임 **3~10개**를 레퍼런스로 조사한다. 각 게임에서 플레이 경험·학습 순서·난이도·목표 등의 **기획**과 이를 만드는 **구현 방식**을 구분해 확인한다. 확인하지 못한 내용을 사실처럼 쓰거나 사례 수를 채우려고 관련 없는 게임을 넣지 않는다. 요청에 맞는 공통점과 차이를 정리하고, 서로 다른 플레이 경험을 빠뜨리지 않도록 일감 후보를 펼친다. 각 후보를 현재 엔진 API·컴포넌트와 대조해 구현 가능한 범위로 좁힌 뒤 일감으로 정의한다. 필요한 엔진 기능이 없거나 확인되지 않으면 그 사실을 주의사항에 적는다. 확인되지 않은 API를 구현 가능한 것으로 단정하지 않는다.

사용자에게 다시 묻지 않는다. 요청에 없는 세부 선택은 확인한 레퍼런스와 엔진 기능을 근거로 정하고, 어떤 기준을 택했는지 일감 내용에 적는다.

- 각 일감에 참고한 게임과 기획·구현 근거, 반영할 기획 의도, 플레이어가 확인할 결과를 적는다. 레퍼런스의 구체적인 설정이나 수치를 그대로 복사하지 않는다.
- **일감 하나에는 하나의 기획 목표와 그 목표를 실현하는 하나의 구현 결과만 담는다.** 제목·내용·완료 확인 항목에 서로 독립적인 목표나 결과가 두 개 이상 있으면 일감을 나눈다. 그 결과에 꼭 필요한 내부 절차는 같은 일감에 둔다.
- `create_project_work_item`을 호출하기 직전에 제목과 모든 `checks`를 다시 본다. 서로 다른 주체의 동작을 각각 확인할 수 있거나 한쪽만 구현해도 다른 쪽의 결과가 남는다면 파일을 나눈다. 예: `근접 공격과 순찰 적`은 `플레이어 근접 공격`과 `적 왕복 순찰`로 분리한다. 공격으로 적이 제거되는 상호작용은 필요한 두 일감을 선행 조건으로 둔 별도 결과인지 판단한다.
- 완성품에 서로 다른 플레이 경험이나 진행 구간이 있으면 먼저 그 결과들을 목록으로 펼친다. 예를 들어 스테이지의 도입·새 도전·응용·도착은 각각 다른 배치와 완료 확인 항목이 필요하면 별도 일감으로 만든다. 스테이지 전체를 구현하는 포괄적인 일감 하나로 대체하지 않는다.
- 각 후보를 따로 구현·확인할 수 있는지 검사한다. 같은 결과를 위한 반복 배치나 내부 계산은 묶고, 독립적인 결과는 나눈다. 일감 수를 미리 정해 억지로 늘리지 않는다.
- 요청한 결과를 독립적으로 구현하고 확인할 수 있는 단위로 나눈다. 방향 계산처럼 한 결과를 만드는 내부 절차는 별도 일감으로 쪼개지 않는다.
- 새 일감을 만들기 전 기존 검색 결과와 제목·내용을 대조한다. 같은 결과를 다루는 일감이 있으면 새 파일을 만들지 않고 그 일감을 이어서 사용한다. 포괄적인 기존 일감에 새로운 독립 결과를 덧붙이지 않는다.
- 발판 착지, 낙사 복귀, 목표 도달처럼 각각 따로 구현·확인할 수 있는 결과를 한 개의 포괄적인 일감으로 묶지 않는다. 각 결과마다 파일 하나를 만들고 선행 관계를 적는다.
- 플레이어가 목표·현재 상태·조작 결과·성공과 실패를 알아야 하는지 확인한다. 필요한 화면 표시와 피드백은 요청에 UI라는 말이 없어도 일감 후보에 포함한다. 예: 체력 표시, 목표 안내, 피해 피드백, 클리어 화면. 각각 독립적으로 구현·확인할 수 있으면 별도 일감으로 나누고, 확인된 엔진 UI 기능과 필요한 선행 일감을 적는다. 필요하지 않은 장식·메뉴·부가 기능은 추가하지 않는다.
- 캐릭터·배경·타일·아이콘 등 화면에 보여야 할 이미지도 확인한다. 현재 `Asset`의 이미지를 재사용할 수 있으면 그 파일과 적용 대상을 적는다. 필요한 이미지가 없으면 **이미지 제작**과 **이미지를 객체·UI에 적용**하는 결과를 별도 일감으로 만든다. 제작 일감에는 용도, 크기·프레임·투명 배경 등 필요한 사양과 확인 항목을 적는다. 이미지 생성 도구가 연결되지 않았다면 생성했다고 표시하거나 임의의 기존 이미지를 완성품으로 대체하지 말고, 제작 일감의 미완료 사유를 기록한다.

각 일감의 `content`에는 다음을 구체적으로 적는다. 제목만 바꿔 같은 설명을 반복하지 않는다.

1. **플레이 경험:** 플레이어가 언제 무엇을 보고, 어떤 선택·행동을 하며, 성공과 실패를 어떻게 알게 되는가. 화면 표시가 필요한 일감은 표시 시점·내용·변화 조건을 적는다.
2. **진행 구성:** 시작 조건, 단계별 변화, 종료 조건. 스테이지라면 구간의 역할과 앞뒤 구간의 연결을 적는다.
3. **구현 범위:** 재사용할 기존 기능, 새로 만들 데이터·객체·동작, 관련 파일이나 API의 확인된 위치. 확인하지 않은 이름은 추측하지 않는다.
4. **설계 기준:** 난이도·거리·시간 등 요청에 중요한 값의 목표와 근거. 실제 플레이로 확인하지 않은 수치는 목표라고 표시한다.
5. **의존 관계와 경계:** 먼저 필요한 일감과 이 일감에서 다루지 않을 결과를 구분한다.

`checks`에는 정상 경로뿐 아니라 중요한 실패·경계 상황도 관찰 가능한 문장으로 적는다. 예를 들어 발판 일감은 착지 가능성과 낙사 후 처리를 구분한다. 항목을 채우려고 같은 조건을 다른 말로 반복하지 않는다.

- 일감마다 256비트 무작위 ID를 만들고, 같은 ID의 파일이 있으면 다시 생성한다.
- 제목, 기능 내용, 주의사항, 검색 키워드와 구체적인 완료 확인 항목을 기록한다. 완료 확인 항목은 관찰 가능한 결과와 조건을 적고 `create_project_work_item`의 `checks`에 전달한다.
- 열린 프로젝트의 `Editor/WorkItems/<일감이름>_<ID>.md`에 일감별로 파일 하나를 저장한다. 파일에 쓸 수 없는 제목 문자는 `_`로 바꾸고 이름은 최대 80자로 줄인다. 기존 `<ID>.md` 문서도 읽을 수 있다. 다른 프로젝트의 일감과 섞지 않는다.
- 저장된 일감은 ID, 제목, 키워드, 내용으로 검색하고 원문을 읽을 수 있어야 한다.

AI 챗에서는 `create_project_work_item`으로 저장하고, `search_project_work_items`로 찾은 뒤 `read_project_work_item`으로 원문을 읽는다.

사용자가 구현을 요청했다면 일감 생성만 보고하고 끝내지 않는다. 생성한 일감들을 순서대로 `wiki/Skills/Pipeline/FeatureImplementation.md`의 기능 구현 단계로 넘긴다. 일감 생성만 요청한 경우에만 여기서 멈춘다.
구현 전에 실패해도 이미 만든 일감 문서는 삭제하지 않는다. 다음 요청에서 검색해 같은 일감을 이어 사용하고, 중복 문서를 만들지 않는다.
