# 파이프라인: 요청 분석

모든 사용자 요청의 첫 단계에서 읽는다. 사용자가 파이프라인 실행을 따로 요청할 필요는 없다.

사용자가 **요청 분석만** 요구하면 그 요청이 무엇을 원하는지 한두 문장으로 알려주고 멈춘다. 파일 조사, 유형 확정, 일감생성, 구현은 진행하지 않는다.

1. 사용자의 요청이 무엇인지 파악하고, 원하는 결과를 짧게 정리한다.
2. 설명·질문·레퍼런스 찾기는 **자료조사**로 분류하고 필요한 정보를 찾아 답한 뒤 종료한다.
3. 프로젝트 변경 요청은 `search_project_work_items`로 관련 일감을 찾고, 있으면 해당 원문을 읽는다. 검색에는 요청 문장 전체가 아닌 핵심 기능 이름을 쓴다. 결과가 0건이면 동의어 또는 더 짧은 핵심어로 한 번 더 찾은 뒤 일감 생성 여부를 판단한다. 일감은 과거 구현의 단서다. 일감이 없으면 **신규구현 후보**로 두되, 현재 프로젝트의 관련 파일과 동작을 확인해 확정한다.
4. 확인한 결과를 **버그수정**, **기능변경**, **코드개선**, **신규구현** 중 하나로 분류한다. 여러 목적이 섞여 있으면 각각 적는다. 분류하지 않은 채 다음 단계로 넘기지 않는다.
   - 기존 기능이 기대와 다르게 동작하면 **버그수정**.
   - 기존 기능의 결과·값을 바꾸면 **기능변경**.
   - 동작을 유지하며 구조·가독성·성능을 개선하면 **코드개선**.
   - 필요한 기능이 현재 없다면 **신규구현**.
   기존 일감이 있어도 해당 기능이 현재 코드에 없을 수 있고, 일감이 없어도 기능은 이미 있을 수 있다. 확인 전에는 **잠정**으로 표시한다. 예를 들어 “Player의 속도를 5로 변경”은 기존 값이 다르면 기능변경, 속도 기능이 없으면 신규구현, 이미 5면 변경할 일이 없다.

다음 단계에는 요청 내용, 관련 일감, 현재 코드 근거, 판단한 유형을 전달한다. **신규구현**은 `wiki/Skills/Pipeline/WorkItemCreation.md`의 일감생성으로 넘어간다. **버그수정·기능변경·코드개선**은 업데이트할 기존 일감을 정하고 원문과 해시를 읽어 **위키 업데이트를 예약**한 뒤 `wiki/Skills/Pipeline/FeatureImplementation.md`의 기능 구현으로 넘어간다. 관련 일감이 없다면 현재 코드로 확인한 기존 기능의 기준 일감을 먼저 만든다. 이 단계에서 작업 크기나 담당자는 정하지 않는다.
