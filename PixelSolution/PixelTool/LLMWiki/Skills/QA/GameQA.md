# 게임 QA

aliases: 게임 테스트, 플레이 테스트, 범용 QA

사용자가 게임 전체의 동작이나 플레이 경험을 QA해 달라고 요청할 때 읽는다. 일감의 완료 확인 항목만 판정하는 `wiki/Skills/Pipeline/Test.md`와 별개로 실행한다. QA에서 확인한 버그는 버그수정 일감으로 만들거나 기존 일감에 연결해 같은 요청에서 수정한다.

1. **규칙 파악:** `search_project_game_rules`로 현재 프로젝트의 저장된 규칙을 먼저 찾고 관련 문서를 읽는다. 시작 파일, 진입 가능한 씬, 입력 처리, 목표·실패·재시작 조건을 현재 코드와 게임 화면 안내에서 확인한다. 저장된 규칙과 현재 구현이 다르면 현재 구현을 따른다. 확인한 규칙과 추측을 구분하고 필요한 파일만 읽는다.
2. **규칙 저장:** 플레이 모드로 들어가기 전에 `search_project_game_rules`를 호출하고 확인한 내용을 `save_project_game_rule`로 `Editor/GameRules`에 저장한다. 전역(`global`), 객체별(`object`), 입력(`input`) 규칙으로 나눠 한 파일에 규칙 하나씩 저장한다. 객체 규칙의 `subject`는 객체명, 전역 규칙은 `Game`, 입력 규칙은 입력을 받는 객체나 화면명으로 지정한다. 입력 키는 `keys`에 기록한다. `basis`에 확인한 파일·줄 또는 실제 관찰 내용을 적고, 확인한 경우만 `confirmed`, 추측은 `inferred`로 표시한다. 같은 제목·대상을 다시 저장할 때는 기존 문서와 해시를 읽고 갱신한다. 규칙을 찾지 못한 항목은 만들지 않는다. 도구가 없거나 저장에 실패하면 그 원인을 보고하고 규칙을 저장했다고 말하지 않는다.
3. **관찰 수단 확인:** 화면 캡처, 게임 상태 조회, 로그, 키·마우스 입력 도구 중 실제 연결된 기능을 확인한다. 화면이나 상태를 볼 수 없으면 위치·조작감·시각 효과를 검증할 수 있다고 가정하지 않는다.
4. **종료 목표:** 현재 게임의 코드와 화면에서 최종 클리어·게임 오버 등 종료 조건과 확인 가능한 신호를 찾는다. 중간 스테이지 진입이나 몇 번의 입력을 게임 완료로 간주하지 않는다. 시작과 조작, 진행·전환, 성공·실패·재시도 시나리오를 종료 목표까지 연결하고 각 단계의 입력·기대 결과·관찰 방법을 정한다.
5. **실제 플레이:** 에디터를 플레이 모드로 전환한다. 이동처럼 지속 입력이 필요한 행동은 `durationMs`로 최대 5초씩 누르고, 점프·공격처럼 한 번 눌러야 하는 행동은 짧은 `frames` 입력을 쓴다. 화면과 새 로그로 위치·스테이지·생명력·진행 변화를 확인하고 다음 입력을 정한다. 필요한 경우 방향키와 점프 같은 키를 함께 누른다. 의미 있는 변화가 있을 때 캡처하고 매 프레임 AI를 호출하지 않는다. 로그는 직전 커서 이후만 읽는다.
6. **종료까지 반복:** 최종 종료 신호를 실제로 관찰할 때까지 입력→관찰→판단을 이어 간다. 실패하면 게임 규칙에 맞게 재시작하고 다른 경로를 시도한다. 같은 지점에서 반복해 진전이 없거나, 입력·관찰 도구로 더 진행할 수 없거나, 실행이 중단되면 그 지점과 이유를 기록하고 멈춘다. 무한 반복을 피하기 위해 한 QA 요청은 최대 10분간 플레이하며, 종료에 도달하지 못하면 '완주 미확인'으로 보고한다. 다음 요청에서는 확인한 진행 구간부터 이어서 계획한다.
7. **플레이 중 규칙 갱신:** 새로 관찰한 입력, 객체 동작, 전역 진행·종료 규칙은 근거와 함께 `save_project_game_rule`로 추가한다. 기존 문서와 같은 규칙이면 읽은 최신 해시로 갱신한다. 코드에서 예상한 규칙과 실제 관찰 결과가 다르면 그 차이를 기록하고 확인되지 않은 내용을 확정 규칙으로 쓰지 않는다.
8. **결과 판정:** 실제 화면·상태·로그가 기대 결과를 뒷받침할 때만 통과로 표시한다. 종료 신호를 보지 못했다면 게임 전체를 통과로 표시하지 않는다. 도달하지 못한 구간과 관찰하지 못한 결과는 미확인으로 남긴다.
9. **환경 복구:** 이 테스트에서 바꾼 모드와 임시 설정을 원상복구한다. 복구하지 못한 상태가 있으면 코드 수정 전에 기록한다.
10. **버그 일감:** 기대 결과와 실제 결과의 차이를 재현 입력·화면·로그·관련 코드로 확인한 항목만 버그로 판정한다. `search_project_work_items`로 같은 결함을 먼저 찾고, 있으면 기존 ID를 재사용한다. 없으면 `create_project_work_item`으로 **서로 독립적인 버그마다 일감 하나**를 만든다. 내용에는 기대·실제 결과, 재현 순서, 관찰 근거, 영향 범위, 주의사항을, `checks`에는 수정 후 확인할 정상·경계 조건을 적는다. 원인을 모르면 관찰된 증상까지만 쓴다. 미확인·재현 불가 항목은 버그 일감으로 단정하지 않고 QA 보고에 남긴다.
11. **구현과 재검증:** 버그 일감을 `wiki/Skills/Pipeline/FeatureImplementation.md`의 **버그수정**으로 넘겨 해당 결함만 수정한다. 수정 후 `wiki/Skills/Pipeline/Test.md`에서 그 일감의 확인 항목을 다시 검사하고, 성공한 실제 변경은 기존 일감 이력에 기록한다. 실패하면 같은 ID를 유지해 그 일감만 다시 수정한다. 도구·권한·엔진 범위 때문에 구현할 수 없으면 일감은 보존하고 막힌 지점을 보고한다.
12. **보고:** 종료 신호의 관찰 여부, 도달한 마지막 구간, 시나리오별 통과·실패·미확인, 생성·재사용한 버그 일감, 수정·재검증 결과를 정리한다. 수정하지 못한 버그를 완료로 표시하지 않는다.

`Editor_Game_Capture`는 요청할 때 현재 Scene View 한 프레임을 PNG로 반환한다. `Editor_Game_KeyInput`과 `test_game_key`는 플레이 모드에서 키 **1~4개를 동시에** 입력한다. `frames`는 1~120프레임, `durationMs`는 실제 시간 100~5000밀리초이며 둘 중 하나를 사용한다. 여러 키에는 `keys`, 단일 키에는 `key`를 쓴다. 게임 상태 조회와 마우스 조작은 아직 제공되지 않는다. 보지 못한 상태나 화면만으로 판단할 수 없는 게임 규칙은 검증했다고 주장하지 않는다. 리임포트 성공과 에러 로그 부재도 게임 QA 통과를 뜻하지 않는다.
