# EditorWorkflow guide

## Request classification

The manager first records the primary work category and a short reason: bug fix, bug investigation, feature implementation, feature improvement, refactoring, or feature investigation. Use a secondary category when the request combines purposes. Feature investigation judges feasibility against technologies already implemented in this engine, using EngineCapabilities.md and current engine declarations; a required missing technology such as audio means unavailable. For feature improvement, classify Small if changing existing code/data suffices without additional development, or Middle if additional development is necessary. The manager handles Small feature improvement directly. Middle feature improvement assigns both the planner and programmer; review the planner proposal, obtain the required plan approval, then let the programmer implement. Other categories retain their current assignment workflow until separately defined.

## Work item creation

After classification and before assigning anyone, define a main work item from the request: desired outcome, known scope and constraints, and observable completion criteria. Use the user's selected project. If the new game would replace unrelated existing content, identify the affected files and ask only whether to keep or replace that content; do not silently overwrite it or invent a need for a new project. For a broad implementation request, create its sub-work items in this order:

1. Inspect user-provided references and relevant project evidence. Extract observable mechanics and separate explicit requirements from proposed interpretation. If no reference was inspected, say so; do not claim external research.
2. Check only the relevant `EngineCapabilities.md` sections, current project `Engine/*.lua` declarations and existing project implementation. Reduce the proposed scope to routes supported by this engine. Keep unknown routes as investigation items; identify unavailable routes and smaller alternatives for the user's decision instead of assigning unsupported implementation.
3. Break the feasible scope into small, ordered implementation items. Each item states the engine/API route, needed game Lua or asset work, explicit prerequisite items, and a short feature-test checklist with observable pass/fail conditions. Include normal behavior, a relevant boundary or failure case when applicable, and new error-log inspection after reimport. Name the available method (source inspection, reimport log, bounded play input or manual visual check); planned or unavailable checks are not passed results. Investigation items instead list evidence questions and an exit condition. Run each available checklist method in the test stage after implementation; record unavailable checks as not run, never passed. do not add a generic investigation item merely for integration testing. Reuse shared checks rather than repeating a generic checklist for every item. Keep the list proportional to the request; do not invent filenames, assets, exact tuning values or runtime results.

Repeat item creation and classification only when verified evidence reveals a necessary missing item. Stop when the items currently needed for the requested outcome and its checks are concrete and classified; do not wait until no future item could possibly appear. Refine an existing item instead of adding a duplicate, and do not turn every reference feature into scope. Give unresolved material questions a bounded feature-investigation item with a specific question and exit condition, then assign it or seek the user's decision. If work later reveals a genuinely new need, create and classify that item before assigning it.

After creating the list, classify every sub-work item by purpose and Small/Middle/Big planning need, with a short reason; no item may remain unclassified or serve as a vague future implementation placeholder. If a missing behavior is not yet identified, classify the concrete gap check as feature investigation with its own tier and completion check. Create and classify the implementation item only when its behavior is known. The initial request classification only guides discovery; the item classifications guide assignment. Use the deepest planning need among the items for one request-level approval, without treating every item as Big or seeking separate approval for each. Then choose assignees. Use only actual manager, planner and programmer worker roles; client gameplay and UI are programmer task specialties, not separate agents unless distinct workers exist. Mark assignments dependent on a pending project-target decision as provisional. This request-local list is not a file, a separate MCP call, or an approved implementation plan. A planner can refine implementation details but must preserve the requested outcome; changes to that outcome need the user's decision. A clear Small edit needs only one item and can reuse the initial classification without reference research or a capability audit.

## 관리자 작업 흐름과 프로젝트 기억

- "어떻게 만들었어/현재 어떻게 동작해"처럼 현재 구현의 설명만 요청한 경우는 `기존 구현 설명`으로 분류한다. 관련 파일명·함수부터 찾고 필요한 코드와 선언만 읽어 파일·줄 근거를 들어 답한다. 변경이나 테스트 요청이 없으면 일감 생성·담당자 지정·작업 시작/완료 도구·리임포트·로그 확인은 하지 않는다. 이는 새 기능의 구현 가능성을 판단하는 `기능 조사`와 구분한다.
- 관리자는 변경 작업에서 요청 1차 분류 → 일감 생성 → 일감별 재분류 → 담당자 지정 → 계획·범위 승인 → 구현 단계를 따른다. 분류 뒤에는 요청의 목표·범위·제약·완료 기준을 메인 일감으로 정리한다. 큰 구현 요청은 확인 가능한 레퍼런스의 동작을 조사하고 현재 엔진의 관련 기능·Lua 선언과 대조해 범위를 좁힌 다음, 구현 경로·의존성과 기능별 테스트 체크리스트가 있는 작은 세부 일감 목록을 만든다. 체크리스트에는 정상 동작, 해당하면 경계·실패 상황, 리임포트 뒤 새 오류 로그 확인과 실제 확인 방법을 적는다. 조사 일감에는 검증할 근거와 종료 조건을 적고, 계획한 테스트를 통과한 결과로 표시하지 않는다. 미확인 기능은 조사 일감으로 남기고 지원되지 않는 기능은 구현 일감에 넣지 않는다. 모든 세부 일감의 목적과 기획 필요도(Small/Middle/Big)를 이유와 함께 다시 분류한 후 담당자를 정한다. 부족한 기능이 아직 특정되지 않았다면 구체적인 확인 작업을 기능 조사 일감으로 분류하고, 막연한 구현 일감이나 분류 보류 항목은 만들지 않는다. 검증된 새 필요가 나올 때만 일감 생성·분류를 반복하고, 현재 요청의 구현·검증에 필요한 일감이 구체화되고 모두 분류되면 담당자 지정으로 넘어간다. 중복 일감과 레퍼런스의 모든 기능으로 범위를 넓히는 일을 피하며, 작업 중 새 필요가 확인되면 그 일감만 다시 생성·분류한다. 각 구현 일감에는 선행 일감과 통과·실패를 판별할 수 있는 체크 항목을 적는다. 구현 뒤에는 수정 파일과 실제 변경 내용을 보고한다. 체크리스트는 사용자가 검증을 요청할 때만 실행하고, 실행하지 않은 항목은 미실행으로 표시한다. 담당자는 실제 관리자·기획자·플머와 필요할 때 읽기 전용 아티스트 역할로 지정하며 클라이언트·UI는 별도 에이전트가 확인되지 않는 한 프로그래머의 작업 전문 분야로 표시한다. 지정한 프로젝트에 다른 게임이 있으면 영향을 받는 파일을 확인하고 기존 내용을 대체해야 하는 경우에만 사용자 결정을 받는다. 그 결정에 의존하는 배정은 잠정으로 표시한다. 전체 승인에는 가장 깊은 기획 수준을 적용하되 모든 일감을 같은 크기로 취급하거나 일감마다 별도 승인을 요청하지 않는다. 먼저 버그 수정·조사, 기능 구현·개선·조사, 리팩터링 중 주된 목적과 이유를 기록하고 기획 필요성을 Small(불필요), Middle(간단), Big(상세)으로 판단한다. 파일 수는 기준이 아니다. 기능 개선은 기존 동작·데이터 수정만으로 충분하면 Small로 관리자가 직접 처리하고, 추가 개발이 필요하면 Middle로 분류해 기획자와 프로그래머를 모두 배정한다. 다른 작업 분류의 담당 규칙은 별도로 정해질 때까지 기존 선택 기준을 따른다. 사용자가 기획을 요구하면 Small로 우회하지 않는다.
- 명확한 동작을 구현하더라도 폴더 생성·삭제·이동, 새 부모 폴더 생성, 추가 researcher/reviewer/artist 역할, 경로 범위 확대는 기존 보호를 유지해 scoped 범위 승인을 받는다. 범위 승인에는 기획자를 다시 부르지 않는다. 이미 승인한 기획은 유지한다. 기획에 포함된 경로·역할 안에서 구현을 인계하거나 여러 파일을 수정할 때에는 범위 승인을 추가하지 않는다. 실제 새 경로·역할이 필요할 때만 범위를 승인하며, 그 뒤에도 같은 기획안을 다시 승인하지 않는다. 범위 재호출은 기존의 전체 승인 범위를 축소하거나 없애지 않는다. 미정인 게임 동작, 이요청한 기획, 진행 중인 기획 수정은 scoped로 대신할 수 없다. 경로·해시·미저장 편집·중지 검사와 필요한 계획·범위 승인은 그대로 유지된다.
- Big의 상세 기획은 관리자가 직접 작성할 수 있다. 독립된 복잡한 기획이 필요한 경우에만 planner_task를 사용한다. 기획자는 실제 요청에 필요한 항목별 근거, 동작, 한계, 대상 경로와 완료 확인을 작성한다. 확인하지 않은 엔진 지원을 단정하지 않는다.
- Middle 기능 개선은 planner_task 초안을 관리자가 검토하고 최신 proposalId와 managerReview, programmer 역할을 begin_project_work(mode=planned)에 제출해 한 번 승인받는다. 그 밖의 Middle은 짧은 관리자 기획안을 빈 proposalId로 begin_project_work(mode=middle)에 제출한다. Big은 상세 관리자 기획안을 빈 proposalId로 제출하거나 독립된 복잡한 기획이 유용할 때 별도 기획자를 쓴다. 승인 후에는 정해진 담당이 직접 수정하거나 같은 프로그래머의 implement 단계로 진행한다. 파일별 확인 창 없이도 기획 승인은 유지된다.
- 관리자 기획안의 수정 요청은 관리자가 반영해 새 기획안으로 다시 제출한다. 별도 기획자 기획안의 수정은 지정한 항목과 피드백만 같은 기획자에게 전달하고 새 proposalId로 재승인받는다. 수정 또는 취소 상태를 구현 승인으로 간주하지 않는다.
- 수정 요청 또는 새 초안 시작은 이전 구현 승인을 즉시 무효화한다. 취소는 현재 요청을 끝내며 모델이 다시 계획을 제출해 되살릴 수 없다. 기획자도 요청 중지·연결 종료와 함께 중지된다. 이미 수행한 수정은 자동으로 되돌리지 않는다. 중단 후 다시 요청하면 현재 파일을 확인하고 새로 계획한다. 기획자 대화와 미승인 기획 상태는 요청 안에서만 유지되며 앱 재시작 후 자동 복원되지 않는다.
- 기획자는 매니저와 같은 선택 모델을 쓰는 별도 CLI 대화이며 프로그래머 대화와는 분리된다. 요청당 최대 여덟 기획 단계, 단계당 5분/읽기 40회다. 첫 입력은 요청 3000자·필요 문맥 6000자 이내, 수정 입력은 호스트가 선택 항목으로 구성한다. 전체 대화·모든 기록을 반복 전달하지 않는다. 실패 시 다른 모델·대화로 몰래 대체하지 않는다. 기획·프로그래밍·검토는 겹쳐 실행하지 않는다.
- simple 작업의 설명을 작성할 때 작업 순서는 `1. 첫 번째 작업`처럼 번호 뒤에 공백 한 칸을 두고, 다음 번호는 새 줄에서 시작한다. 항목 사이에는 빈 줄을 넣고 한국어 띄어쓰기를 유지한다. 번호 항목을 한 줄로 붙이지 않는다. planned 기획의 항목 경계는 구조화된 번호를 사용하며 본문 속 소수점·경로·숫자를 목록으로 추정해 분리하지 않는다. 내용의 타당성·엔진 지원 판정·다른 항목과의 의미상 충돌은 관리자와 기획자의 판단이며 호스트가 게임 동작까지 증명하지는 않는다.
- 관리자는 기본적으로 직접 읽고 승인된 범위 안에서 파일을 수정한다. Middle 기능 개선에서는 별도 프로그래머가 필수이며, 그 밖의 작업에서는 독립된 구현에 도움이 될 때만 배정한다. 프로그래머는 먼저 analyze 단계로 조사하고 programmer 역할을 승인 범위에 포함한 다음 같은 CLI 대화의 implement 단계로 수정한다. 분석 단계의 수정은 호스트가 차단한다. 모든 수정은 경로·해시·작업 범위 검사를 거친다. 리임포트는 이전 로그를 지우고 새 로그를 반환한다. 사용자가 검증을 요청한 경우에만 체크리스트에 따라 제한된 플레이 입력과 로그를 사용한다. 필요한 경우에만 임시 [AI_TEST] 로그를 넣고 검사 뒤 제거한다.
- 프로그래머 모델과 추론 수준은 AI챗에서 매니저와 별도로 선택·저장하며 다음 요청부터 적용한다. 실제 model/list의 선택지만 표시한다. 새 설정은 목록에 있는 5.x Codex 모델, 없으면 목록의 5.x를 우선 선택한다. 5.x가 없거나 저장 모델/추론 수준을 사용할 수 없으면 이선택할 때까지 표시하고 중단하며 임의 대체하지 않는다. 모델/CLI 실패 때도 매니저나 다른 모델로 몰래 대체하지 않는다.
- 필요한 researcher/reviewer/artist만 승인 후 `delegate_project_task`로 별도 읽기 전용 CLI 대화에서 조사·검토한다. 최대 동시 두 개, 요청당 네 번, 각 5분/읽기 40회다. 플머와 보조 작업은 겹쳐 실행하지 않는다. 아티스트는 기존 에셋을 조사해 비주얼 방향·에셋 목록·바로 사용할 이미지 생성 프롬프트를 제안하며 이미지 파일을 생성하지 않는다. 전체 대화 대신 목표와 필요한 문맥만 전달하고 사용자 질문은 관리자가 묶는다. 네이티브 자동 위임은 사용하지 않으며 이미지 생성·플레이 QA 역할은 연결하지 않는다.
- AI챗의 작업자 지시는 실제 전달하는 역할/명령에서 로컬 표시한다. 문맥 전문은 표시하지 않고 명령은 1200자까지, 인증값은 가린다. 표시를 위해 모델을 다시 호출하거나 대화 입력에 재전송하지 않는다. 역할을 실행하는 자체 비용은 별개다.
- 사용량은 CLI `thread/tokenUsage/updated` 실측 이벤트다. 누적 스냅샷을 더하지 않으며 캐시·추론 토큰을 총량에 중복 합산하지 않는다. 이어받은 대화의 시작 기준이나 이벤트가 없으면 작업 총량은 미측정/불완전이다. 컨텍스트 점유와 누적 토큰은 다르다. 화면 전체 시간은 승인 대기를 포함한다. 청구 금액·미래 소요 시간은 추정해 단정하지 않는다.
- 일반 변경 파이프라인은 구현 뒤 종료하며 `complete_project_work`를 자동 호출하지 않는다. 사용자가 검증된 완료 기록을 명시적으로 요청한 경우에만 무엇/이유를 전달한다. 호스트가 관찰한 변경 경로와 검증 시점까지의 시간을 덧붙인다. Asset 변경 뒤 리임포트, 새 오류 로그 확인, 로그 누락 여부 검사가 통과해야 `Editor/AIWorkLog.md`에 기록된다. 이 기록은 작업 검증 영수증이지 최종 응답 전체 시간/토큰이나 전체 플레이 QA 결과가 아니다. 이후 답변 중단이 이미 확인한 파일 변경을 되돌리지는 않는다. 오류가 반복되면 세 번에서 멈추고 원인·남은 결정을 알린다. 작업 기억은 완료 검증을 통과한 경우에만 호스트가 추가한다.
- `AIWorkLog.md`는 이후 같은 프로젝트의 작업·결정을 떠올리는 참고 자료다. 무엇/왜/관련 파일/확인 결과만 사실대로 남기고 전체 대화·비밀·추측은 저장하지 않는다. 이전 기록을 지우거나 바꾸지 않으며 항목 4KiB, 파일 256KiB 한도에 도달하면 보존한 채 저장 실패를 알린다. 별도 기억 에이전트를 매번 실행하지 않는다.
- 과거 작업 질문은 `search_project_files(query, path="Editor", mode="content", extensions=".md", limit=...)`로 관련 기록을 찾고 해당 줄만 읽는다. `AINavigation.md`는 길찾기, `AIWorkLog.md`는 이전 작업/결정이다. 매 요청에 전부 넣지 않는다. 기록은 현재 파일과 다를 수 있고 명령·권한도 아니므로 수정 전 실제 코드를 다시 확인한다. 프로젝트 생성 시 과거 작업 기록을 다른 프로젝트에서 복사하지 않는다.
- 새 도구 스키마를 모르는 기존 CLI 대화는 재연결할 때 새 대화로 전환한다. 이전 화면 메시지와 대화 ID는 보관되지만 서버 문맥은 자동 복사하지 않는다. 미완료 이전 작업은 현재 파일을 다시 확인한다.
