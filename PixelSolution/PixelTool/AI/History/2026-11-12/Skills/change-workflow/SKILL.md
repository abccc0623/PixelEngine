# Change workflow

1. Classify the request by purpose: bug fix, bug investigation, feature implementation, feature improvement, refactoring or feature investigation. Give a short reason. Estimate planning need: Small needs no design, Middle a short plan, Big detailed design. File count is not the criterion.
2. Before assigning roles, create a request-local main item with goal, scope, constraints and observable completion criteria. For broad work, inspect available references and relevant `EngineCapabilities.md` sections and current `Engine/*.lua` declarations. Narrow scope to supported routes. Make ordered sub-items with implementation route, dependencies and a short checklist: normal behavior, applicable boundary or failure, fresh error logs after reimport and available check method. Investigation items have a specific evidence question and exit condition. Label uninspected references as proposals; exclude unavailable features unless the user chooses an alternative.
3. Classify every sub-item by purpose and Small/Middle/Big with a reason. Do not leave a vague implementation placeholder. Repeat creation and classification only for newly verified needs. Refine duplicates and stop when current work and checks are concrete and classified. If a new need appears later, classify that item before assignment. Use the deepest required tier for one request-level approval; keep smaller items at their own tier.
4. Assign only available manager, planner and programmer roles. Client gameplay and UI are programmer specialties. The manager handles clear Small work directly. For Middle feature improvement needing additional development, use both planner and programmer. Other programmer assignments are optional for bounded independent work. If a requested game would replace unrelated content, identify affected files and obtain the user's keep-or-replace decision before dependent work.
5. Before edits, register exact paths with `begin_project_work`. Small uses `simple`; ordinary Middle uses `middle` with a concise manager plan; Big uses `planned` with a detailed manager plan or a separate planner when useful. Middle feature improvement requires `planner_task(draft)`, manager review, and `begin_project_work(mode=planned)` with the current `proposalId`, `managerReview` and programmer role. Present the first plan through begin_project_work rather than asking for approval in ordinary text or ask_choice. Use one host-confirmed approval for the unchanged plan. Revise with the same planner and obtain fresh approval. A canceled or stale plan grants no edits. Folders, new parent paths, optional read-only roles and scope expansion retain `scoped` approval; scoped cannot replace design approval. The 20-path budget applies.
6. After approval, the manager edits through permission- and hash-checked tools unless a programmer was assigned. That programmer analyzes before approval and implements afterward in the same conversation; do not bypass a failed assigned worker. Optional researcher, reviewer and artist roles are read-only and used only when helpful. The artist produces visual direction and image prompts, not images.
7. After implementation, report the changed files and what was changed. Mark checklist checks not run unless actually observed. Do not automatically enter test or completion stages, reimport, inspect logs, run gameplay checks, or call `complete_project_work`. If the user explicitly requests validation, follow `game-feature-test/SKILL.md` for gameplay checks and report the observed results. Failed tool calls are logged by the host in `Editor/AIToolFailures.md`.

The item list is not a file or approval. Follow `AIRestrictions.md`, applicable guides and host checks throughout.
